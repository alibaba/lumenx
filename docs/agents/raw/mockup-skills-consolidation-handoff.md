## 2. Skill 1 — `visual-shelf` (built, in production)

### What it does

Turns a folder of visual reference images into a self-contained
brand-book HTML page with palette extraction (poetic names + hex),
live HTML/CSS reproductions of 2-3 distinctive effects per image,
plain-Chinese-first design-terminology teaching, and cross-image
visual DNA when ≥3 images. On request, applies the DNA to a target
project as a design-system page + mockup.

### Modes (natural-language dispatched, no flags)

| User says | Mode | Output |
|---|---|---|
| "看一下这批参考" / "分析这批图" + folder | **Shelf** | `shelf.html` + `notes.md` |
| "提取 DNA / 共性" + folder | **DNA** | same files; DNA section deepened (≥4 patterns + union palette + filename evidence) |
| "把这风格用到 `<target>`" + folder + target path | **Apply** | + `design-system.html` + `mockup.html` + `visual-dna-source.md` in target |

### Location

`~/.claude/skills/visual-shelf/`
- `SKILL.md` (252 lines)
- `references/shelf-html-spec.md`
- `references/apply-mode-spec.md`
- `references/examples.md`
- `references/anti-patterns.md` (11 anti-patterns, severity-ordered)

### Score / status

- Scored 92.5/100 via `/darwin-skill`
- Real-world tested on the canvas-UX inspiration batch
  (`docs/design/references/2026-05-24-canvas-ux-inspiration/shelf.html`
  — generated by the skill, ~1100 lines)

### Key rules worth preserving in any consolidation

1. **Honesty trumps volume** — if an effect can't be reproduced in
   HTML/CSS, say so plainly + show partial approximation. Padded
   reproductions teach false patterns.
2. **Chinese-first explanations + English term in parens** —
   "弥散光晕（diffuse aura）". Never English-only (gatekeeping) or
   Chinese-only (loses vocabulary onboarding).
3. **Poetic palette names** — "Ink in Water", not "Color 3".
4. **No mono-caps for chrome labels** — only the build-label footer
   may use `JetBrains Mono` + `uppercase`. Everywhere else is sentence-case Inter.
5. **No markdown syntax inside HTML output** — recurring bug class:
   `**bold**` leaks into HTML and renders literally. Grep for `\*\*`
   before saving any `.html` file.
6. **Reserve padding for absolute-positioned overlays** — palette
   cards needed 38px top padding for the hex pill so it wouldn't
   overlap the poetic name.
7. **Cross-image DNA is the highest-value output at scale** — treat
   as research finding with filename evidence, not summary paragraph.
8. **Preserve `<!-- edited by user -->` entries verbatim** + never
   silently overwrite Apply-mode target files.

## 3. Skill 2 — `design-preview` (concept, not built)

### What it does (per user's process doc)

Generates a single-file HTML mockup showing **before / after** of a
proposed visual change to an existing codebase, so the user can
decide before any PR is opened. Layout: PS-style draggable
comparison divider + tabs for multiple component scenarios +
bottom "diff list" with per-item mini live demos.

### The critical v1 vs v2 distinction (the heart of this skill)

| Variant | BEFORE source | Use case | Audience |
|---|---|---|---|
| **v1 · Showcase** | Typical AI/Tailwind slop (purple-pink gradients, emoji, decorative borders) | Marketing / case study / onboarding | External / promotional |
| **v2 · Real-code** | Strictly reconstructed from actual repo source | Implementation decision, PR planning, ROI estimation | Internal / engineering review |

**The single biggest documented pitfall**: producing a v1 showcase
and letting the user review it as if it were v2 decision artifact.
The inflated BEFORE→AFTER delta misleads the user about
implementation cost / payoff (because the BEFORE is a strawman).
This actually happened in the original incident (process doc §9
timeline, steps 2-6) — 5 iterations of work had to be redone after
the user finally said "the BEFORE doesn't look like my actual site."

### Dispatch rules

- **Default** → v2 (decision artifact)
- "做个 marketing 对比 / 宣传案例" → v1
- "先看看升级前后对比" → v2; **explicitly tell the user**
  "this is v2 based on real code from `<file paths>`"
- Both needed → file names must distinguish:
  - `<feature>-mockup-v1-showcase.html`
  - `<feature>-mockup-v2-real.html`

### Hard rule for v2 — must Read real code FIRST

Per user's documented lesson:

> 最大教训：如果 Phase 1（读真实代码）一开始就做，后续 5 个迭代
> 里至少 3 个可以省掉。这就是为什么"先读真实代码"必须是流程的
> 硬约束，不是 nice-to-have。

For v2 the agent MUST:
1. Read all source files for components being compared
2. Note exact CSS variables / Tailwind classes / chrome elements
3. List diffs in three categories: **Add (+)** / **Modify (~)** / **Remove (−)**
4. **Each diff must be grep-able in real code** — if grep can't
   find it, it doesn't belong in the v2 diff list

### Output structure

- Top page header + **type banner** (states v1 or v2 + BEFORE source)
- Tabs to switch between component scenarios
- PS-style draggable divider (BEFORE bottom layer, AFTER `clip-path: inset`)
- **BEFORE / AFTER badges placed OUTSIDE the compare container**
  (legend bar). Earlier mistake: putting them inside got them
  clipped by `clip-path`.
- Bottom "component diff list" — each entry with mini live demo:
  - Add: single demo
  - Modify: paired before→after
  - Remove: removed item + strikethrough
- Honesty placeholder cards for any scenario that can't be mocked
  (don't fabricate content)
- Phase 5 hard stop: **do NOT auto-implement based on the mockup**;
  wait for user feedback

### Tech stack

- Single-file HTML + vanilla JS + inline CSS
- Google Fonts: JetBrains Mono + Inter (no framework CDNs)
- Draggable divider: `mousedown` → window `mousemove`/`mouseup`,
  `requestAnimationFrame` throttled
- Mobile: horizontal cut → vertical cut via `@media (max-width: 960px)`
- Hard cap: ~2500 lines HTML (matches `visual-shelf`)

### Output location

```
docs/agents/deliverables/
├── <feature>-mockup.html              ← if single version
├── <feature>-mockup-v1-showcase.html  ← marketing
└── <feature>-mockup-v2-real.html      ← decision
```

## 4. Analysis — why two skills (vs one merged)

| Dimension | visual-shelf | design-preview |
|---|---|---|
| Input | image folder (external inspiration) | code changes (internal proposal) |
| Output medium | scroll-browse magazine | drag-compare + diff list interaction |
| Core action | absorb DNA from references | get user sign-off pre-PR |
| Hard rule | no faking reproductions | **must Read real code first** + v1/v2 distinction |
| Audience mindset | learner / seeking inspiration | decider / reviewer |
| Failure mode | wrong palette / wrong glossary | **v1 mistaken for v2 → decision corrupted** |

Merger risks diluting design-preview's "must read real code +
strict v1/v2 distinction" — that rule is the line between
trustworthy decision artifact and accidental misinformation. It
shouldn't share mental airspace with shelf's "extract palette from
image" flow.

But "two fully separate skills + maintenance overhead" is also
imperfect. Real shared concerns:

- Single-file HTML, no framework CDN
- ~2500-line cap, Google Fonts only (Inter + JetBrains Mono)
- "Don't write markdown syntax inside HTML output"
- "Reserve padding for absolute-positioned overlays"
- Sentence-case + no mono-caps chrome
- Output reviewable in browser; agent does NOT auto-implement

A `_common/visual-deliverable-conventions.md` referenced by both
skills was the original recommendation. The user's new consolidation
idea may replace this with something better.

## 5. Candidate consolidation patterns (not prescriptive)

The user has a specific consolidation idea but didn't disclose it.
Possibilities the next session might explore:

1. **Plugin / sub-skill pattern** — one parent skill `visual-deliverables`
   with internal modules sharing a shell, specialized per mode.
2. **Convention library + thin skills** — most logic lives in shared
   reference docs; each skill is a small dispatch shell.
3. **Single skill, strict mode tree** — one skill with strong Phase 0
   dispatch (Shelf / DNA / Apply / Showcase / Real-review), each
   mode's discipline rules pinned to that mode.
4. **Filesystem bundle** — group at the path level
   (e.g., `~/.claude/skills/visual/{shelf,preview}/`) with shared
   `_common/` sibling, but separate SKILL.md files.

Whichever pattern is chosen, **two non-negotiables** from this
analysis:

- **The "must Read real code" rule for v2 must survive** whatever
  architecture is used. Don't let it be diluted.
- **The v1 vs v2 distinction must be enforced at the entry point**.
  The agent can't accidentally produce v1 when the user wanted v2.
  This is the cost-of-failure case from the documented incident.
