# LumenX 渐进重构与验证计划

计划核对：2026-10-09。本文维护实施协议、切片、唯一依赖顺序与门禁；实际进度只见 [执行台账](EXECUTION-STATUS.md)，职责关系见 [README](README.md)。原计划及逐片审查保留在研发来源快照；未随公开候选发布的审查不能当作公开可复核证据。本文保留实施合同，当前结果以公开候选台账为准。

## 1. 目标、范围与完成条件

本轮要把已经存在的共享 Core 落实成可检验的共同契约：相同受支持的创作意图保持相同含义，接纳和保存有明确成功边界，已提交任务能够查询恢复，产品继续独立组织创作流程。随后验证本地使用、独立项目复制到 ECS，以及浏览器和桌面访问两种环境。

用户已确认 Q1–Q9：A 本地单用户为基础，B 远程单用户是本轮具体试用目标；C 多人协作只保留身份、状态所有权和并发接口边界，不实现协作功能。浏览器和桌面都是正式操作入口。项目携带采用独立复制，不增加双向同步。Q9 的自动恢复查询属于本轮，不可降为无限期后续事项。

用户授权：优劣明确的工程决策由助手列出依据后决定；仅实质改变产品承诺、使用方式、成本或不可逆数据行为的分支再次讨论。因此本文的常规工程决定不逐项请求批准。ECS 域名、接入方式和复制界面等细节留到试用准备时处理，不阻塞共同契约与安全边界设计。

全部完成须同时具备以下证据：

1. 功能覆盖矩阵包含每个当前交付功能的前端行为、后端契约、异常行为、实际测试入口和最近执行结果；没有“只有测试文件名”却标为已覆盖的条目。
2. Studio、Atelier、Playground 及 Agent 在各自声明支持的范围内，共用规范化规则和供应商执行契约；不支持的输入在付费前明确拒绝。
3. 接纳时完整有效参数可靠保存；显式 `0`、`false`、合法 `-1` 不被缺省覆盖；失败重试不采用更新后的默认；旧记录缺失的历史值不被伪造。
4. 保存失败不向用户确认成功、不触发后续新付费提交；重放不重复派发，旧 attempt 不覆盖新 attempt，Agent 授权仍在提交时有效。
5. 已可靠保存 provider handle 的可查询任务，重启后继续查询原任务并取回成果，提交计数不增加；不确定状态可观察。
6. 受控数据通过浏览器/桌面 × 本地/ECS 四组合验收；无独立服务器仍可在本机运行。复制得到独立可编辑项目，媒体可用，原项目不变。
7. 每个实施切片记录固定提交、所跑命令、通过/失败/跳过、隔离范围及已知限制；构建通过、模拟生成通过、真实供应商通过分别报告。

本轮不做微服务、分布式队列、多人账户/协作同步、全库事件溯源、强行统一产品状态或批量重写历史项目；也不新增依赖，除非后来出现明确需要并取得用户授权。

## 5. 生成生命周期与状态所有权

### 身份不能混为一个 ID

- **request ID / receipt**：识别同一入口对同一意图的重复投递；同 ID 不同规范化 payload 是冲突，不能悄悄新生成。
- **产品任务/候选 ID**：由产品聚合拥有，表示哪一个 Studio 分镜任务、Atelier 候选或 Playground 输出。
- **attempt ID/token**：一次执行的所有权和写回守卫；已知失败后的重试获得新 attempt，冻结意图不变。
- **授权上下文**：人工发起或 Agent turn/tool call、批准范围、取消状态；不能用 request ID 代替权限检查。
- **provider handle**：provider、远端任务 ID、必要 request ID/查询区域等非密钥信息，用于查询同一远端任务。
- **artifact 与采纳关系**：生成文件和产品选择分别记录；候选完成不等于被用户采纳。

### 接纳 → 持久化 → 付费提交 → handle 保存 → 恢复

1. 请求身份认证与项目访问权限检查先行，再按调用方/项目范围及 request ID 查找 receipt。已有记录使用录入时的稳定请求指纹/契约版本核对重复投递；相同则返回原冻结接纳结果，新增候选列表为空；不同则报告冲突。这个路径不按新 catalog 默认重新解析，因此默认更新不能制造伪冲突或再派发；receipt 也不能绕过当前访问权限。
2. 新意图先在预览阶段完成入口适配与 Core 规范化：明确输入角色，校验入口/模型能力，固定有效参数和受管媒体版本；形成带契约/规则/预设版本的意图指纹与成本依据。Agent 的批准绑定这份内容及允许范围，不能仅绑定工具名或未解析的参数。
3. 接纳核对同一份预览/获批意图，再检查项目归属和容量。catalog、预设、媒体版本或参数变化后，不能在旧批准下重新解析并执行不同内容：原冻结内容仍合法时可执行原内容；需要改变则重新预览/批准。建立 receipt、产品任务/候选、attempt 和冻结快照，**可靠保存后**返回可派发接纳结果。显式参数与省略状态、预设来源和解析规则版本保留。
4. 执行前重新核验当前 attempt、取消与权限/批准内容指纹，确认固定媒体版本可传输；保存“准备提交”状态，成功后才调用 provider。这个状态只证明准备发生，不证明远端接纳或未接纳。
5. provider 返回 handle 后立刻可靠保存；保存失败不能仅写日志后继续报告成功。若写入恢复材料，它必须绑定同一产品任务和 attempt，只用于重放未完成的持久化，不成为第二份任务权威；导入时校验归属、去重并通过当前 attempt 写回守卫，不能据它另建或重新提交任务。保存完全不可用时明确报告状态待确认。
6. 独立 query 路径凭 handle 和提交时的 provider/账号范围/region/workspace/endpoint 标识及 credential 引用跟踪任务，不采用当前默认 provider。可轮换引用指向的凭据值，不能暗中改变账号或查询环境；凭据不可用时明确反馈。完成后取回媒体到调用方指定的受管位置；产品按 attempt/owner 守卫提交结果。完成保存失败保留文件和可重放的结果关联，不删除已付费媒体。
7. 重启取得单写者所有权后，扫描已接纳记录：只有持久协议能证明尚未进入提交阶段的排队任务，才可在原授权仍有效且未取消时继续原任务；旧 schema 缺少该证明不能猜测。已有充分 handle/查询环境的任务查询恢复，即使生成参数快照不完整；跨提交不确定窗口或查询身份不足的任务进入待确认，不自动付费重发。
8. 已知 provider 失败后的人工重试使用原完整快照、新 attempt；不完整历史快照只限制重新付费执行，查询/取回原任务按第 6–7 项处理。网络超时/查询异常本身不建立“失败可重试”的事实。

请求重放去重和本地互斥不能保证跨网络恰好一次计费。供应商若有可验证的幂等键或按客户端请求标识查询，可缩小“已接纳但 handle 未落盘”的窗口；是否支持必须逐 adapter 调查，不能假设统一支持。

公共执行接缝只接收规范化意图、授权/attempt 所需上下文、产物位置和可失败的诊断持久化回调，返回明确的 handle/状态/产物/错误类别。它不自动创建第二份产品任务，不自动选候选，不隐式重新提交。

各产品保留聚合和采纳状态，但共享 attempt/提交/查询状态转移规则及同一组契约测试，由薄的产品存储适配承载。不能把渐进共享方案实施成三套 receipt、提交、恢复协议；规则复用不要求先集中所有产品任务数据。

媒体哈希本身不能防止接纳后内容被替换。付费提交必须使用固定受管媒体版本对应的传输地址；重签只改变访问凭据，不能改变内容。无法固定或旧内容已删除时明确失败或形成新意图，不能转取同 URL 的新内容后静默付费。自动随机属于已知的生成策略；供应商未返回实际 seed 时，不捏造确定值，也不承诺再次生成像素相同。

恢复回归必须分别覆盖：①快照不完整但 handle/账号/region 足够，允许查询取回；②handle 缺失，不自动提交，仅使用已证实支持的客户端标识查询，否则待确认；③账号/region/workspace 不明，不用当前默认猜测查询。三者不是同一种“历史不完整”。

每个独立功能切片小提交并遵循仓库 Lore 规则。协议/schema 的改变保留旧记录读能力；回滚前检查新记录是否仍可被旧版本读取，不能把 `git revert` 误作数据回滚方案。跨产品拆目录晚于行为收敛，不用文件行数作为验收指标。

## 7. 故障预演（3 类）

| 失败场景 | 可能根因 | 防止/发现 | 必须得到的结果 |
|---|---|---|---|
| **同一次生成被重复付费** | 网络响应丢失、提交后 handle 未保存、HTTP/Agent 重放、恢复误调 submit、取消与执行竞争 | receipt+payload 绑定；提交前 attempt/授权核验；可失败的 handle 保存；query 单独接口；在全部边界注入中断并计数 provider submit | 已有 handle 的恢复只查询；未知状态不自动发新请求；旧 attempt 不写回；无法证明外部幂等时准确报告不确定性 |
| **重构后项目“保存成功”但数据或媒体丢失** | 原地覆盖 JSON、吞错、第二进程全量旧快照覆盖、旧 tab 全量 node.data、工程复制半完成 | 原子保存+失败回滚、writer guard、revision/局部命令、媒体 manifest、导入 staging/提交边界；磁盘故障与并发测试 | 旧有效数据保留；用户看见保存失败/冲突；已付费媒体可找回；源项目和目标未完成导入互不污染 |
| **本地/ECS 或桌面连接了错误环境，或把私有资料暴露** | 仅凭端口判断 ready、共享固定缓存键、默认对外监听、静态挂载整个 output、桌面远程仍启动本地服务 | health 环境身份与协议版本；缓存按环境隔离；默认 loopback；请求/媒体访问控制；占端口/错误响应/未授权请求/四组合试用 | 不接受错误服务为 ready；不串项目和配置；未授权看不到项目/内部 JSON/媒体；桌面只终止自己拥有的本地进程 |

## 8. 扩展测试策略与证据口径

2026-10-28 执行约束（按用户最新要求）：优先复用现有服务、状态、工具与隔离环境，只解决可复现缺口；没有实际需求时不增加防御状态机、抽象层或验证框架。每片先锁关键行为，再跑受影响文件和直接相邻测试；仅测试/说明窄修时保留未变生产代码的已有结果，补验改动范围。完整前后端构建和代表性浏览器旅程集中于最终整合版本；出现新失败或未解决风险才扩大检查。保留原失败和准确范围，不以重复次数替代覆盖质量。

### 测试环境先于测试收集

在不含用户 `.env`、运行数据和供应商凭据的独立固定提交工作区实施；测试进程使用明确的临时数据/配置路径和允许列表环境变量，阻止真实网络、预热及工具下载。隔离必须在导入 `api.py`/`pipeline.py` 及收集测试前生效；`pytest --basetemp` 或构造 pipeline 后改路径都不充分。不能在共享根目录用一次全量 pytest 来探测这些副作用。

测试收集清单与功能矩阵比对，显式纳入位于 `src/apps/comic_gen/` 的目标测试或把它们迁入已有测试入口；其中 shared-asset HTTP 测试目前可能因 import 失败而 skip，必须把未收集、收集但跳过、真实执行通过分别记录。新收集到的失败要判定是真问题、fixture 不安全还是已过时，不能直接加 skip。Atelier 的 region/skills/agent_runtime 等 fixture 也存在先构造后换路径的情况，隔离需覆盖整套测试，不只修 Studio 示例。真实 FFmpeg 测试单列工具依赖和短合成媒体；不访问用户生成成果。

全量功能目录直接引用主代理的 [TEST-MATRIX.md](../../context/lumenx-first-principles/TEST-MATRIX.md)，包含 44 个功能组，本稿不复制另一份清单。实施证据至少关联：`功能/产品/用户行为/API或服务/现有测试/收集入口/缺口/新增验证/最近固定提交与结果`。覆盖目标是“每个交付功能有能验证其契约的测试”；不设一个百分比后把未测的重要入口隐藏起来。高风险保存/付费/权限/恢复要求 happy path 与边界故障，低风险展示变化用对应组件/集成覆盖，不为逐行覆盖写镜像测试。

## 9. 回滚与停止条件

### 后续增量方案：可版本化视频 Skill（不新增 P0–P10 编号）

在 P3/P4 的共同能力、Agent 审批和执行快照基础上，增加版本化 Product Skill 层。系统默认 Skill 包负责提供镜头规划、连续性、提示词编译、生成接纳和视频 QC；用户可复制并优化自己的 Skill，账户或项目级显式绑定后生效。每次运行先解析 `system → workspace → user → project → session draft`，再生成不可变 `effective_skill_snapshot`，并把内容哈希写入审批、生成回执、恢复和 QC 记录。

该增量方案不改变 Studio、Atelier 的状态所有权，也不允许 Skill 直接执行任意代码或绕过现有工具白名单、能力校验、审批、计费、媒体冻结和恢复协议。外部 Skill 文档只能作为人工审核后的编译输入；用户优化通过草稿、沙箱评测、显式激活和回滚完成。先实现只读规划和非付费 QC，再接入视频生成接纳，最后接入用户反馈优化。

进入条件：P3 的参数/媒体快照与 P4 的 Agent 授权回归通过；Skill manifest、作用域绑定、哈希校验、工具权限交集和运行快照测试齐备。退出条件：用户 Skill 不能改变已批准任务的有效参数，不能重复付费，不能跨用户读取或写入项目，系统 Skill 更新可差异比较并回滚。

### 云端目标与部署分级（不改变既有 P0–P10 依赖）

项目未来以云服务器运行作为目标部署形态。先交付单机云端 MVP：单数据根、单写进程、静态前端、FFmpeg、HTTPS、已编译 Product Skill 和可恢复任务回执；该级别只面向单用户或小规模内测。随后再建设多用户生产：PostgreSQL、对象存储、队列、隔离 worker、Skill registry、租户权限、配额/积分、审计和真实 Provider 回执。

云端 MVP 不自动加载开发者本机 Skill，不执行外部任意脚本，不允许通过共享卷多副本或增加 workers 绕过单写者边界。多用户生产的进入条件包括租户隔离、Skill sandbox、队列幂等、媒体访问、Provider 真实任务恢复、图片/视频/音频计费、备份恢复和 HTTPS 登录现场证据。单机验收通过不得写成多用户生产通过。

- 任一切片发生静默改参、丢失原有能力、重复付费提交、越权、假保存或覆盖其他 attempt，先修复该切片及回归，不能以“后续统一”带过。
- 新旧 schema 的读写兼容和备份/恢复试验完成前，不对用户项目执行批量迁移；导入复制使用受控副本验证。
- Qoder 的未提交工作持续变化时只更新保护清单，停止依赖该版本的集成操作，继续不依赖它的隔离基础/契约/安全测试；不对其 worktree 做修复、测试启动、合并或清理。
- 外部服务不支持查询或幂等不是阻止整个 Q9 的理由：按 adapter 明确能力，支持者自动查询，其他保持待确认。禁止把不支持者包装成自动恢复成功。
- 本计划不记录运行进度；执行者按台账中的就绪切片、用户已有授权和阶段边界推进，不发例行“是否继续”问题。遇到新增承诺或不可逆数据行为才回到相应决策。

## 11. 真正尚缺的事实与决策

**可以继续调查、不需要现在问用户的事实：** 各供应商 query/取消/按客户端标识查询的能力及限制；Wan 3.0 参考音频与输出音轨的官方契约（不能仅凭旧 `audio_url` 与引用数组字段名推断相同含义）；分支最新固定提交及可合法纳入的 A 增强；现有测试收集/运行器支持范围；各数据聚合的跨文件写入依赖；工程引用/媒体种类和历史 schema。

**到执行现场才需要的输入：** ECS 目标环境/现有服务/实际接入信息、真实模型验证的费用范围，以及工程复制试用选择的项目。现在不询问域名、按钮位置或包格式偏好，也不把缺现场信息变成停止本地隔离工作和设计收束的理由。

**当前没有必须再次选择的实质产品分支。** 若官方能力与“保留明确 false”“既有参考音频语义”出现真实冲突，先形成准确案例与兼容方案，再仅就无法由已确认原则决定的行为提问。若要扩大到多人并发、离线自动同步、迁移删除源项目或提高自动付费权限，才属于新产品决定。

## 12. 执行协作建议

可用原生角色包括 planner、architect、critic、executor、test-engineer、verifier、explore/researcher。本计划由 Planner 起草，经 Architect 与 Critic 顺序审查并修订，主代理负责整合；写者与审查者分开。

后续实施以一个 executor 负责当前纵向切片、一个 test-engineer 负责独立验收夹具、verifier 检查证据为轻量配置；架构/迁移/权限边界用 high 推理，普通适配与回归用 medium。共享 `api.py/pipeline.py` 在同一时段只有一个写入负责人，测试和 UI 仅在文件所有权独立时并行。每次交接提供固定提交、文件范围、执行结果和未解决风险。
